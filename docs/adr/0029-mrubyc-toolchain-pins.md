# ADR-0029: mruby/c capability and Zephyr SDK pin policy

## Status

Accepted — implemented in the same change that introduces `mrubyc`.

## Context

The contract gains an `mrubyc` block that embeds the mruby/c VM and
compiled Ruby bytecode (authored by ux-creator) into product firmware.
Targets: 8-bit AVR, Zephyr (all major supported MCUs plus FPGA soft
cores), nRF Connect SDK, and Emscripten for CI/browser legs. Two
decisions needed pinning:

1. **Which mruby/c revision.** `release4.0.0` predates the upstream
   `hal/avr`, `hal/esp32` and `hal/rp2040` trees and the
   `MRBC_USE_FLOAT=0`/`MRBC_USE_STRING=0` feature-off macros the VM flag
   gate relies on (upstream PRs #286/#289/#293/#294/#298). Only a master
   commit covers every required HAL.
2. **Which Zephyr tree per SDK.** Nordic silicon only builds through the
   nRF Connect SDK fork; everything else should track upstream Zephyr.

## Decision

- Pin mruby/c to master commit `2dec4802b09be1fc12f388d3c9267ffd9dc6c404`
  (sha256-verified tarball in `docker/third_party.manifest`), exposed as
  `/opt/mrubyc/REF` so the `fw.mrubyc` gate can compare it to
  `mrubyc.ref`. Revisit the pin when a release carrying the AVR/ESP32/
  RP2040 HALs ships. OpenBlink was evaluated as reference material only
  and is not adopted.
- Pin `mrbc` to mruby `4.0.0` (RITE0400 bytecode).
- **Nordic targets** build against the nRF Connect SDK **LTS** line —
  v3.4.1 today (`sdk: "nrf-connect"`). Minimal module set: `nrf`,
  `zephyr`, `nrfxlib`, `hal/nordic`, `hal/cmsis`, `hal/cmsis_6`,
  `lib/picolibc`.
- **Non-Nordic Zephyr targets** build against **Canonical's Zephyr
  26.04 LTS** distribution (`sdk: "zephyr"`). Canonical maintains
  Launchpad forks of upstream Zephyr 4.4 and its module repositories
  and pins a tested source set through `zephyr-manifest@26.04.0`
  (<https://git.launchpad.net/~arctic-tern/zephyr-rtos/+git/zephyr-manifest>).
  The image clones the `zephyr` fork at the manifest-pinned commit
  (`2e4ba3e7c1823597ae82edf9f9406a6cdf262873`, verified by
  `git rev-parse HEAD` in `docker/fetch-pins.sh`); module revisions in
  the Canonical manifest are identical to upstream v4.4.2, so modules
  stay sha256-pinned GitHub tarballs. Canonical's Workshop dev
  environment (snap + LXD) cannot run inside Docker and is not used.
  When the first upstream 4.x LTS (planned Zephyr 4.6, April 2027)
  ships, the pin moves to that LTS line; long support windows matter
  for embedded firmware.
- Boards run through the `west` backend, implemented as direct
  `cmake -DBOARD= -DZEPHYR_BASE=` so the image needs no west venv at
  runtime. `toolchain: "cross-compile"` + `cross_prefix` selects
  non-ARM toolchains (e.g. `riscv64-unknown-elf-` for HiFive1, ESP32-C3,
  Nios V, Mi-V and other FPGA soft cores).
- Emscripten legs share the dashboard image's digest-pinned
  `emscripten/emsdk:6.0.10` stage and run under the `node` simulation
  runner so CI exercises the same `.rb` logic that ships.

## Consequences

- One toolchain image covers AVR (`avr-gcc`), RISC-V
  (`riscv64-unknown-elf`), ARM (`gnuarmemb`), Xtensa (platformio),
  Emscripten and both Zephyr trees without a runtime west install.
- Any upstream Zephyr board can be targeted by adding an MCU profile
  JSON plus `backend: west`; no new HAL code ships in this repo.
- The `fw.mrubyc` gate fails closed on stale generated bytecode, a
  ref/toolchain mismatch, feature flags the VM cannot run, or a UX
  manifest whose requirements exceed the configured VM flags.
- NCS `trusted-firmware-m` is intentionally excluded; nRF91/nRF54L
  builds target the plain (non-NS) board qualifiers.
